# PR templates and agent instructions

Research snapshot: 2026-10-27. Links below pin the revisions inspected so later policy changes do not change the evidence behind this comparison.

## Sample and limits

The strongest matches are OpenClaw and Goose: both explicitly welcome AI-assisted contributions and require authors to understand and verify the result. OpenCode explicitly addresses AI-generated PR descriptions. Cline and Continue provide useful adjacent examples of agent setup and AI review. These documents establish AI-aware contribution workflows; they do **not** establish what percentage of each project's code is AI-generated.

Neither an AI disclosure field nor an agent transcript is a substitute for a useful explanation and evidence.

## Agent instructions

| ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [OpenClaw AGENTS.md](https://github.com/openclaw/openclaw/blob/caf3034ae08157264c43e8e085a68f892ac5b5cd/AGENTS.md)  | Sets a size limit, routes detailed guidance to its owner, and refers to scoped instructions. Requires real reproduction and behavior evidence, records gaps, and discourages speculative scope growth. | Keep the root file a compact entry point. Preserve package-specific design and testing rules in their existing owner. Distinguish observed results from assumptions.                                                       |
| [OpenCode AGENTS.md](https://github.com/anomalyco/opencode/blob/6abf95b947cf6f452a3901ac8cbfe6efa670c7ca/AGENTS.md) | Documents concrete code-generation commands, dependency boundaries, default branch, and where tests must run. Asks tests to exercise implementation rather than duplicate its logic.                   | Include verified commands with their working directory and consequential repository constraints. Do not import another project's branch, tool, or style preferences.                                                       |
| [Goose AGENTS.md](https://github.com/block/goose/blob/8a16788137c8af25f9d6d17ee87bbedb53ea9325/AGENTS.md)           | Provides setup, command examples, a small directory map, and concise GitHub communication guidance. Calls out generated-code boundaries and specific operational gotchas.                              | Give agents a short map and a reliable path from change to verification. Keep descriptions focused on decisions and outcomes.                                                                                              |
| [Cline AGENTS.md](https://github.com/cline/cline/blob/56296682a23d6cb2bcf4faec334cc3a298539551/AGENTS.md)           | Explains build prerequisites, package-specific commands, credentials needed for real agent turns, and environment-specific limitations.                                                                | Record prerequisites that affect correctness, especially building before tests that spawn the compiled CLI. Avoid copying machine-specific installed-state claims or permanently exempting a test based on a past failure. |

These are patterns to adapt, not proof that every rule in a large agent file improves outcomes. The existing package instructions already cover CLI contracts, external-tool verification, behavior-focused tests, and LLP design records; duplicating them in the root would create competing sources of truth.

## Recommended convergence

These recommendations are the synthesis of the comparison and this repository's requirements, rather than rules all sampled projects share.

1. **Keep different openings.** Features explain capability and motivation. Bug fixes explain the symptom and trigger, expected versus actual behavior, and minimal reproduction steps. Maintenance changes use a short summary.
2. **Keep alternatives explicit.** Explain the chosen approach and the credible alternatives actually considered. Do not invent rejected designs to fill the template. Put long design reasoning in the owning LLP and link it.
3. **Use evidence, not future intent.** Record commands or manual steps actually run, outcomes, relevant environment, and gaps. For bugs, identify the observed failure before the fix and the result afterward; say when reproducing it was not possible. Mention planned checks separately.
4. **Make visuals optional and useful.** A short command/output example, Mermaid diagram, or linked interactive artifact can explain a CLI change. Screenshots suit visible changes. An illustrative artifact does not prove the implementation works.
5. **Keep consequential caveats visible.** State compatibility changes, migrations, required user actions, and unresolved uncertainty when relevant. Avoid ritual risk sections for ordinary changes.
6. **Make root AGENTS.md a routing and execution guide.** Include repository layout, scoped-guidance links, exact setup/check commands, verification prerequisites, focused-change expectations, and a link to the PR template.
7. **Keep instructions durable.** Maintain detailed design/test rules in their owning package. Avoid transient task notes, absolute local paths, copied tool prompts, unsupported CI claims, and redundant agent-specific versions of the same instructions.
8. **Treat AI authorship as an implementation detail.** Require understandable changes and accurate evidence from every author. Avoid model-name fields, transcripts, generic attestation checklists, or automated-review promises without corresponding tooling.
