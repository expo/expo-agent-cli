## Summary

[confirmed — Kudo, 2026-09-08] Extend `agents:setup` into an interactive setup command that works both inside an Expo project and outside a project. Let the user choose home or project installation, show the proposed setup, and ask for confirmation before making changes. Install the Expo plugin for detected Claude Code/Codex agents and use `expo/skills` for other agents. When an Expo project is available, also run the existing `skills:sync`. Keep the current `CLAUDE.md`/`AGENTS.md` generator behavior unchanged.

This document records the agreed direction and implementation tasks. It remains Draft because implementation details and verification are unfinished. Its original filename is retained under the corpus's stable-path convention.

## Confirmed product requirements

[confirmed — Kudo, 2026-09-08]

- Keep the entry point `agents:setup`.
- Permit setup without a project root or an installed Expo package. Outside a project, install into the user's home.
- Be interactive by default and obtain user confirmation before setup.
- Let the user choose user-home or project-root installation when a project is available.
- Detect Claude Code and install its Expo plugin using `claude plugin install expo@claude-plugins-official`.
- Detect Codex and run these commands in order: `codex plugin marketplace add expo/skills --ref main`, then `codex plugin add expo@expo-plugins`.
- Otherwise, install skills with `bunx skills add expo/skills --skill '*'`, or the equivalent `npx` command.
- When a project root is available, also run `skills:sync` there.
- Keep the existing instruction-file generators as they are. No new generated skill guidance, docs index, or global instruction-file generator is included.
- No additional HeroUI-inspired work or local documentation mirror is needed.

## Setup flow

[inferred — implementation choices derived from the requirements]

1. **Inspect without writing.** Resolve an optional Expo project root and detect agents, available executables, and existing Expo plugin/skill installations. The setup entry point must no longer require `findUpExpoAppRootOrAssert` to succeed before offering installation. Leave the strict project guards of other commands intact.
2. **Choose targets and scope.** Show detected agents as selectable targets. If both Claude Code and Codex are selected, set up both. For other selected agents, use the skills installer. If no agent is detected, offer the skills path with agent selection. Offer Project and User home when a project exists, defaulting to Project; otherwise offer User home. Show the actual destination and any installer-specific limitations.
3. **Show the complete plan and confirm.** Include selected agents, installer commands, scope, marketplace registration, and any project skill sync or existing instruction-file generation. Declining or cancelling performs no installs, file writes, or selection-cache writes. Keep detection and plan assembly read-only until confirmation.
4. **Install confirmed targets.** Run each installer through its supported interface, with explicit scope options where available. Register the Codex marketplace before installing `expo@expo-plugins`; do not substitute a curated-marketplace plugin. Prefer `bunx` for skills when available, otherwise use `npx`. Pass `*` as a literal argument rather than shell-expanding it. Select only the confirmed agents and scope in the upstream installer.
5. **Run project work when available.** With an Expo project root, compose the existing `skills:sync` and instruction-file generation. The official plugin/skills installation scope and project module sync are separate: choosing User home inside a project still includes project `skills:sync` and current generators unless the existing opt-outs disable them. Without a project, skip module sync and generators; do not create a home-level `AGENTS.md` or `CLAUDE.md`.
6. **Report each outcome.** Distinguish installed, already present, skipped, failed, and action required. Report effective scope, destination, source, and restart/authentication requirements when known. A plugin installation does not prove that its MCP service is authenticated or that the current session has loaded it.

## Compatibility and details to settle during implementation

[inferred — proposed defaults unless stated otherwise]

- **Project discovery versus installed dependencies:** a declared Expo app without `node_modules` is still a project. Official knowledge installation must work there. Attempt the project sync through its existing contract and report unavailable dependencies clearly; do not install Expo automatically. Outside an Expo app, offer home setup instead of treating an unrelated package as an Expo project.
- **Automation:** add `--yes` to accept the displayed setup plan and `--scope user|project` to express the destination without prompting; retain explicit `--agent`. Non-TTY runs without confirmation must exit promptly with actionable instructions, not hang or silently consent. `--json` alone is not consent. Settle validation and exit codes against existing conventions.
- **Existing opt-outs:** preserve `--no-agents-md` for generators. Preserve `--no-agent-skills` for package module sync; use a separate proposed `--no-plugins` flag to skip the new official plugin/skills installation phase. Document that this phase includes the skills fallback. Final flag naming is an implementation detail, not a confirmed requirement.
- **Scope support:** verify each real installer can honor the selected scope. Do not invent a Codex project-scope option or silently perform a home install after Project was selected. If an installer only supports user scope, expose that limitation before confirmation and offer the supported home installation or a project skills alternative explicitly.
- **Reruns:** reuse installations in the requested scope and reuse the matching Codex marketplace. Do not overwrite a different marketplace source with the same name, replace custom plugins, duplicate standalone skills for an agent already served by its plugin, or run broad updates. A global plugin cache alone does not prove project activation.
- **Ownership:** plugin/skills installer files remain owned by those installers. Existing module `skills:sync` and `skills:clean` must not remove them. Deduplicate shared skill directories and report occupied names or cross-agent overlap without deleting user content.
- **Failure isolation:** preserve completed work and report partial failure. Do not turn a failed plugin command into an unannounced standalone skills installation. Keep JSON output machine-readable and external installer progress on stderr. Determine the final exit-code mapping before implementation.

## Acceptance criteria and test plan

- Home setup: no `package.json`, no Expo dependency, or an unrelated package no longer blocks official knowledge setup. User scope is shown and confirmed. No project sync, generated instruction file, or `.expo` cache is written into the current directory or home by the project-only phase.
- Project setup: from the app root or a nested directory, choose Project or User home; install knowledge in the chosen scope and run module sync in the app root. Existing generators produce the same content and preserve user-owned text and `CLAUDE.md` behavior.
- Detection and dispatch: Claude only, Codex only, both selected, other agents, and no detected agent. Assert Claude's exact plugin identifier, Codex's marketplace source/ref and installation order, and the literal skills wildcard. Test bunx preference and npx fallback.
- Confirmation: accepting executes the displayed plan; declining, EOF, and cancellation cause no writes or installer invocations. Non-TTY without explicit consent terminates clearly. `--yes`, `--scope`, `--agent`, opt-outs, and `--json` behave consistently.
- Scope: test each supported installer scope and unsupported combinations; never silently widen Project to User home. Cover spaces in paths, custom home/config roots, missing dependencies, and monorepo selection.
- Reruns and ownership: existing installations and marketplace registration are reused; conflicting sources are reported; managed module links do not overwrite or clean up plugin/skills installer files.
- Failures: missing/broken binaries, unsupported flags, marketplace failure, network/authentication errors, timeout, malformed inspection output, install failure, and project sync failure. Assert partial results, useful recovery information, correct exit codes, and one JSON object on stdout.
- Automated validation: use flat BDD groups with lowercase `should` test names. Add unit tests for planning and result normalization; subprocess e2e for exact argv, interaction/cancellation, home/project files, and JSON. Run focused agents/skills tests, command-surface checks, typecheck, and lint. Update existing setup evals to use the explicit noninteractive path.
- Manual validation: run the built CLI in scratch home/project environments using actual supported installer binaries. Verify each effective scope and plugin discovery in a new agent session; report any authentication still required. Existing generators need regression verification, not new content tests.
