# Changelog

## Unpublished

### 🛠 Breaking changes

- A foreground `dev` stops when this project's dev server is already running, with `DEV_SERVER_RUNNING` (exit 20), instead of starting a second Metro on the next free port that `status` and `dev:stop` could not see. The message names the port and the pid and recovers into `smoke --<platform>` when the server answers, or `status` while it is still starting; `dev --plan` lists no steps and reports `devServerPort.state: 'running'`. `dev --detach` still reports the running server with exit 0, and the plain `start` wrapper is unchanged. ([#157](https://github.com/expo/expo-agent-cli/pull/157) by [@vonovak](https://github.com/vonovak))
- The `package.json` config key is `expo.agent-cli`, not `expo.agentCli`. Nothing inside it changed: `target`, `buildBackend`, `ios` and `android` are the same. A project still on the old key gets an error naming the new one rather than having its settings read as absent. ([#85](https://github.com/expo/expo-agent-cli/pull/85) by [@kudo](https://github.com/kudo))
- `status --explain` is removed, with no alias. Every `status` now reports the changed sources, the OTA verdict and the EAS build lookup, cached under `.expo`, and `--build`, `--device` and `--device-timeout` work on their own; `builds.askedEas` in `--json` now means EAS was called on this run. ([#71](https://github.com/expo/expo-agent-cli/pull/71) by [@kudo](https://github.com/kudo))
- `dev` and `smoke` no longer build on EAS just because this machine cannot build locally. That route is still described (`--plan`, `status`), with a reason saying an EAS build and an EAS Simulator session use EAS credits, but a bare run stops: `dev` exits 1 with `EAS_ROUTE_NOT_CHOSEN` naming `--eas` and `--local`, and `smoke` fails its start phase the same way before spawning anything. `--eas` on the command line, or `buildBackend: "eas"` under `expo.agent-cli` in `package.json`, takes the route with no stop, as before. ([#41](https://github.com/expo/expo-agent-cli/pull/41) by [@kudo](https://github.com/kudo))
- `--cloud` is `--eas` on `smoke`, `navigate`, `runtime:reload` and `runtime:stop`, the flag `dev` already used for the same service. One name now means "on EAS", for the build and for the device. `--cloud` is removed, with no alias: it is an unknown option now. Every command line this CLI prints says `--eas`. ([#34](https://github.com/expo/expo-agent-cli/pull/34) by [@kudo](https://github.com/kudo))
- `dev` now requires a platform flag (`--ios`, `--android`, or `--web`), like `smoke`. The plan always acts on the named platform: a fresh plan runs `expo start --<platform>`, which boots a simulator or an emulator and opens the app, and a stale plan prebuilds and builds through `expo run:<platform>`. A run with no platform exits 1 with a one-line usage error. Every suggestion the CLI prints now states a platform too. ([#7](https://github.com/expo/expo-agent-cli/pull/7) by [@kudo](https://github.com/kudo))

### 🎉 New features

- `deviceBackend` in `expo.agent-cli` puts the app on an EAS Simulator session, top-level or per platform. `dev` then takes the `--eas` route, and so does `smoke` when it starts its own dev server. It builds on EAS too. ([#176](https://github.com/expo/expo-agent-cli/pull/176) by [@kudo](https://github.com/kudo))
- EAS-backed commands no longer spawn `eas-cli@latest`. A global `eas` that resolves to the `eas-cli` package at 25.0.0 or newer is run directly, with no runner and no registry request. Without one, the runner gets the bare `eas-cli` spec, so `bunx` reuses its cached copy instead of reinstalling on every run. A project that declares `eas-cli` still runs its own copy. Printed command lines follow the same choice: `eas …` with a recent global install, otherwise `npx --yes eas-cli …` or `bunx eas-cli …`. ([#159](https://github.com/expo/expo-agent-cli/pull/159) by [@kudo](https://github.com/kudo))
- `navigate` and `smoke` now suppress onboarding, the floating Tools button, and automatic dev-menu opening when launching a development build. Set `EXPO_NO_DEV_MENU=0` to opt out.
- `status --json` reports this worktree's bindings under `binding`. With no device bound on the platform, `next` is a `dev` command (the plan's own when it is already `dev`, else `dev --<platform> --detach --wait-ready`), except for `--web`, an EAS session, or a host where `dev` binds no device. With an unreadable binding file, `next` removes it first (`rm -f '<path>' && …`). ([#TBD](https://github.com/expo/expo-agent-cli/pull/TBD) by [@vonovak](https://github.com/vonovak))
- `dev --device <name|udid|serial>` binds a simulator or an Android device the user names. The CLI never shuts it down or deletes it, refuses a device bound to another live worktree, refuses a serial `adb` lists as `offline` or `unauthorized` with `explicit-not-ready` (exit 7) and names what readies it, and `dev --plan` says it will refuse. The plan's `explicitDevice` says the same on `--json` and on the `cli:start_plan` event. A run that binds no local device (`--web`, `AGENT_CLI_NO_DEVICE=1`, iOS off macOS, no Android SDK) refuses `--device` with `BAD_ARGS`. ([#TBD](https://github.com/expo/expo-agent-cli/pull/TBD) by [@vonovak](https://github.com/vonovak))
- `dev`, `smoke` and `dev:stop` reap the devices of other worktrees: a deleted worktree's created simulator is deleted, an expired one is shut down on the next iOS acquisition, and a spawned emulator instance whose worktree is gone or whose lease expired is killed, or reported `device-gone` when its pid has exited or runs another program; `dev:stop --json` lists them under `reaped`. A delete or kill that fails keeps the binding, so the next reap tries again, and `dev:stop` exits 20 with a How line naming the command that does it by hand. ([#TBD](https://github.com/expo/expo-agent-cli/pull/TBD) by [@vonovak](https://github.com/vonovak))
- `smoke --ios` and `smoke --android` release the device they bound when the run ends: a child dev server's device through `dev:stop --release`, a device bound next to a reused dev server through the boot phase's cleanup. `smoke --no-start` binds and releases nothing. The report names that device, how the run got it, and what its release did: a `device` line, and `environment.boundDevice` in `--json`. A run that binds nothing and uses the worktree's bound device names it as `already bound · kept` (action `existing`). When no app attached and the run put its dev server and device back, the follow-ups start them again with `dev --<platform> --detach --wait-ready` before `navigate`, and a repeated `smoke` keeps `--port`. ([#TBD](https://github.com/expo/expo-agent-cli/pull/TBD) by [@vonovak](https://github.com/vonovak))
- `dev:stop --release` parks the worktree's created simulator and ends its spawned emulator instance once this worktree's dev server is stopped; plain `dev:stop` keeps them and reports them under `devices` with `released: null`; `false` means a release failed. ([#TBD](https://github.com/expo/expo-agent-cli/pull/TBD) by [@vonovak](https://github.com/vonovak))
- A running dev server (`dev`, its detached child, and `start`) and each build step of `dev` renew the worktree's device lease every five minutes, so a session longer than the 60-minute lease keeps its device. A lost lease is reported once each time it is lost, naming `dev --<platform> --detach --wait-ready`, with `--eas` for an EAS Simulator session, to bind the device again. ([#TBD](https://github.com/expo/expo-agent-cli/pull/TBD) by [@vonovak](https://github.com/vonovak))
- `dev --android` binds an Android emulator instance of its own to the git worktree it runs in, and every verb of that worktree uses it. The instance is a read-only emulator of the first AVD, started by this CLI with `-avd <avd> -ports <port>,<port+1> -no-snapshot-save -read-only` on the first free even console port from 5554 to 5584, so two worktrees run two instances of one AVD side by side and neither writes the AVD's image; the binding records its serial and pid, the boot is verified with `sys.boot_completed`, and the build and install steps carry `--device <serial>` (`expo run:android` matches a serial since SDK 58). `navigate`, `runtime:reload`, `runtime:stop` and `status` read the binding through `adb get-state` and never pick the first `adb` device: with no binding they refuse with `NO_BOUND_DEVICE` (exit 20) and name `dev --android --detach --wait-ready`. `smoke --android` gets its instance from the binding, installs the app onto it, and leaves it bound; nothing runs `adb emu kill` any more. When every console port is taken, `dev` refuses `DEVICE_UNAVAILABLE` (`no-free-port`) naming each serial and the worktree it is bound to. An `adb` call that exits non-zero fails with `ADB_FAILED`, quoting adb's stderr. On a host with no Android SDK, `dev --android` binds nothing and serves for a device elsewhere, as before. ([#TBD](https://github.com/expo/expo-agent-cli/pull/TBD) by [@vonovak](https://github.com/vonovak))
- `dev --ios` binds an iOS simulator of its own to the git worktree it runs in, and every verb of that worktree uses it. The simulator is one this CLI created, named `agent-cli <digest>`, or the one the worktree bound before; it is booted with `simctl bootstatus -b`, the build and install steps carry `--device <udid>`, and the open deep-links to it. `navigate`, `runtime:reload`, `runtime:stop` and `status` read the binding, extend its 60-minute lease, and never pick the first booted simulator: with no binding they refuse with `NO_BOUND_DEVICE` (exit 20) and name `dev --ios --detach --wait-ready`. `dev --detach` on a running server boots the worktree's own simulator and refuses `not-reusable` when it has none; a device refusal in the detached child reaches the caller with its own code, exit and `Try:` line. `smoke --ios` gets its simulator from the binding too and leaves it bound. The bindings live under `<expo home>/agent-cli/bindings`, written under one machine-wide lock. ([#134](https://github.com/expo/expo-agent-cli/pull/134) by [@vonovak](https://github.com/vonovak))
- `status` reports what the app installed on a device was built from. It reads the fingerprint a debug build embeds (`expo-constants`, SDK 58+) out of the app on an Android device or a booted iOS simulator, compares it with the project's fingerprint for that platform, and says `up to date`, `rebuild required` or `unknown`, with the commands that fix a stale one. On an older SDK it says the app cannot be checked and reads no device. Right about a build somebody else made, which the freshness line cannot be. Android reads a few hundred KB of the APK through `adb` instead of pulling it; `--device <name>` narrows the read to one device. ([#59](https://github.com/expo/expo-agent-cli/pull/59) by [@vonovak](https://github.com/vonovak))
- The OTA verdict of `status` no longer runs `expo config` for a project with no app config file. ([#70](https://github.com/expo/expo-agent-cli/pull/70) by [@kudo](https://github.com/kudo))
- `status` remembers an EAS "no build" answer for five minutes and shows its age (`none (as of 2m ago)`); `--no-fingerprint-cache` asks EAS again. A project whose static app config names no `extra.eas.projectId` is not sent to EAS; `status` reports `unknown` with the `eas init` command. ([#69](https://github.com/expo/expo-agent-cli/pull/69) by [@kudo](https://github.com/kudo))
- `status --device <phone>` reads the app on a physical iPhone. `devicectl` exposes no app container, so the app is launched with a one-time URL and posts its embedded fingerprint back over the LAN; it needs a debug build whose `expo-dev-client` answers the check. Naming the phone is the consent, because the probe launches the app and `status` otherwise starts nothing. `--device-timeout <secs>` bounds how long the phone gets to answer. A phone that does not answer in time reads as unknown. ([#90](https://github.com/expo/expo-agent-cli/pull/90) by [@vonovak](https://github.com/vonovak))
- `smoke --eas` brings its own EAS Simulator session the way `smoke` boots a simulator: its dev server starts through `dev --eas` (tunnelled; a build the plan needs is the simulator profile on EAS), the session in progress on the platform is reused, and otherwise one is started with Expo Go or with the finished EAS build of this fingerprint — and stopped again when the run ends. A development build with no finished build on EAS is a failed `start-session` phase naming `dev --eas`; the gate never compiles. `dev:stop --eas` also ends this project's session, by id, and reports it under `session`. ([#37](https://github.com/expo/expo-agent-cli/pull/37) by [@kudo](https://github.com/kudo))
- `dev --eas` runs everything on EAS: the dev server is tunnelled, a native build (when the plan needs one) is the `development-simulator` profile on EAS Build — added to `eas.json` when it is missing, and skipped when EAS already has a finished build of this fingerprint — and the app is opened on this project's EAS Simulator session, which is started with Expo Go or with that build when none is up. `--eas` refuses `--web`, `--lan` and `--localhost`, and runs no `eas build:configure` — the profile it needs is the whole of what it writes. Before, `--eas` moved only the build, and did nothing at all for an Expo Go project. ([#36](https://github.com/expo/expo-agent-cli/pull/36) by [@kudo](https://github.com/kudo))
- `dev` opens the app itself once its dev server is up, through the same device tools `smoke` and `navigate` use: it boots a simulator or an emulator when none is up, installs the Expo Go release the project's SDK ships when it is missing, and deep-links through `simctl`/`adb` — never AppleScript, so it works headless and needs no macOS Automation grant. The platform flag no longer reaches `expo start` at all. ([#7](https://github.com/expo/expo-agent-cli/pull/7) by [@kudo](https://github.com/kudo))
- `dev --no-open` serves without opening the app, for a caller that opens it itself — `smoke` starts its dev server this way. ([#7](https://github.com/expo/expo-agent-cli/pull/7) by [@kudo](https://github.com/kudo))
- Initial agent-cli work. ([#49654](https://github.com/expo/expo-agent-cli/pull/1) by [@kudo](https://github.com/kudo))

### 🐛 Bug fixes

- `runtime:stop --eas` on an Android session asks the controller once more when its `close` ran out of time ("process remained running after close"), instead of exiting 1. About 1 stop in 3 on an EAS Expo Go session hit this. ([#211](https://github.com/expo/expo-agent-cli/pull/211) by [@vonovak](https://github.com/vonovak))
- The entry-bundle check that runs before `runtime:tree`, `runtime:tap`, `runtime:type`, `runtime:reload` and `smoke` sends its HEAD to the dev server it was given, never to the tunnel host the manifest names. Through the Expo tunnel that HEAD closed every websocket on the tunnel, the app's debugger socket too, so on a dev server started with `--tunnel` (every EAS Simulator session) every runtime read answered "No target found". ([#197](https://github.com/expo/expo-agent-cli/pull/197) by [@vonovak](https://github.com/vonovak))
- `navigate` and `runtime:reload` read the URL scheme of a dynamic `app.config.js`/`.ts` by evaluating it with `@expo/config` after the project's env files are loaded, the way `expo config` does, and say when that fails instead of reporting "no scheme field was found"; `inspect:config-plugins` reads the declared plugins out of the evaluated config, so a project whose config is code no longer marks every plugin `declared: false`. ([#173](https://github.com/expo/expo-agent-cli/pull/173) by [@kudo](https://github.com/kudo))
- A `smoke` run that has no device to photograph names the `dev` command that binds one: the screenshot row keeps the How line of the registry's refusal instead of its first line only. ([#195](https://github.com/expo/expo-agent-cli/pull/195) by [@kudo](https://github.com/kudo))
- `dev --detach --wait-ready` rejects another project's Metro and follows its own child's port changes within the original timeout. The same readiness check applies when reusing a running server.
- Discovery skips a dev server whose `/status` names another project root, on the scanned ports and on the port `start.log` names, and reports the foreign servers in `status` when nothing else answered. A `/status` that does not answer within 3 s is not accepted. The dev-server lock never publishes a port that serves another project, named on the command line or not. ([#132](https://github.com/expo/expo-agent-cli/pull/132) by [@vonovak](https://github.com/vonovak))
- `status --explain`, the `--eas` device commands, and a failed `eas` step of `dev` no longer quote the first line of the EAS CLI's "project not configured" message with the `eas init` forms cut off. They say the project is not linked to an EAS project and name `npx --yes eas-cli@latest init --account <account> --non-interactive`, with the account filled in when EAS listed one — the answer `deploy` already gave. An unlinked project is its own needs-human scenario, `eas-project-unlinked` (`EAS_PROJECT_NOT_LINKED`), where the generic `eas-prompt` row used to answer for it and tell the caller to answer a question in a terminal. ([#38](https://github.com/expo/expo-agent-cli/pull/38) by [@kudo](https://github.com/kudo))
- `dev --eas` no longer builds the `development` profile, which is a device build no simulator can install — not the EAS Simulator, and not the one on this Mac, so the `eas build:run` the old plan suggested could not have installed it either. ([#36](https://github.com/expo/expo-agent-cli/pull/36) by [@kudo](https://github.com/kudo))
- `inspect:build-log` now locates a `bun install` dependency 404. EAS builds a bun-lockfile project with bun, whose error shape is nothing like npm's, so those failures were unlocatable before. ([#15](https://github.com/expo/expo-agent-cli/pull/15) by [@kudo](https://github.com/kudo))
- Commands no longer suggest a bare `smoke`, which exits 1 now that the gate requires `--ios` or `--android`. Every next-action that named it — on `dev`, `dev:logs`, `typecheck`, the interact commands, `runtime:reload`, `runtime:eval`, `navigate`, and the `AGENTS.md` written into a project — names a platform, and a lint rule fails on any printed `smoke` that does not. ([#6](https://github.com/expo/expo-agent-cli/pull/6) by [@kudo](https://github.com/kudo))
- The Expo Go check now compares native modules against a vendored autolink dump of Expo Go, and falls back to `bundledNativeModules.json` for an SDK this CLI has not recaptured. ([#3](https://github.com/expo/expo-agent-cli/pull/3) by [@kudo](https://github.com/kudo))
- `smoke` now installs Expo Go on a simulator that has not got it, rather than refusing and naming `expo start`. Only for the plan's Expo Go rule, so a project set to `dev-build` or one that cannot run in Expo Go is unaffected. The install also pre-approves Expo Go's URL schemes and marks the developer-menu onboarding seen, without which the deep link raises a dialog nobody answers and the screenshot is a picture of an onboarding sheet. ([#2](https://github.com/expo/expo-agent-cli/pull/2) by [@kudo](https://github.com/kudo))
- `smoke` no longer trusts an installed Expo Go without checking its version. The release the project's SDK ships is compared exactly, the way `@expo/cli`'s `ExpoGoInstaller` does, and any other version — older, newer, or from another release line — is replaced with the right one rather than reported. The expected release comes from the `expo-go` CLI as a subprocess. Under `--no-start` nothing is installed and a wrong version blocks the pass instead. ([#2](https://github.com/expo/expo-agent-cli/pull/2) by [@kudo](https://github.com/kudo))
- `smoke` and `navigate` no longer target Expo Go for a project that cannot run in it. The deep-link decision now reads the same Expo Go compatibility the plan engine and `status` read, and `smoke` will not report `passed` when the app that answered is an Expo Go the project's native code is not in. ([#2](https://github.com/expo/expo-agent-cli/pull/2) by [@kudo](https://github.com/kudo))
- `smoke` now reloads an app that was already running onto the code on disk before it reads it, so the gate no longer passes an app whose error window and screenshot are from before the edit. A reload it cannot prove is `inconclusive` rather than `passed`, and `--no-reload` opts out. ([#2](https://github.com/expo/expo-agent-cli/pull/2) by [@kudo](https://github.com/kudo))
- `dev --detach` no longer reports a detached dev server for a plan step that opens the app and is then refused by macOS after the lock appeared. The grace window that catches that refusal no longer requires `--wait-ready`, so a `dev --detach --ios` now spends it before reporting. ([#2](https://github.com/expo/expo-agent-cli/pull/2) by [@kudo](https://github.com/kudo))
- `runtime:tree` and the interaction commands find the focused screen of an expo-router 58 app on the native stack, JS tabs and the drawer, so they read the screen on top, not every mounted screen. The JS stack, JS top tabs and headless `ui` tabs still report no focused screen. ([#199](https://github.com/expo/expo-agent-cli/pull/199) by [@vonovak](https://github.com/vonovak))
- `navigate` percent-encodes the route and a full URL, so a link with spaces or diacritics opens instead of failing with APP_NOT_INSTALLED. ([#198](https://github.com/expo/expo-agent-cli/pull/198) by [@vonovak](https://github.com/vonovak))
- `smoke` asks an app it opened or reloaded again for 5 s after its first "method not found", instead of reporting a runtime with no debugger. ([#201](https://github.com/expo/expo-agent-cli/pull/201) by [@vonovak](https://github.com/vonovak))
- `status` with an EAS Simulator session on record and no app connected now names the session's platform (`navigate / --<p> --eas`), and with an app connected its `smoke --<p> --eas` step says the session is recorded, not checked, and that if it ended, smoke starts a new billed session only for Expo Go or a finished simulator build. ([#208](https://github.com/expo/expo-agent-cli/pull/208) by [@vonovak](https://github.com/vonovak))
- `smoke` asks for its device again in a later phase when an earlier lookup failed, instead of keeping that failure for the rest of the run. ([#202](https://github.com/expo/expo-agent-cli/pull/202) by [@vonovak](https://github.com/vonovak))
- Runtime reads on an EAS Simulator session now read the session's app when it is the one unclaimed debugger target, also with `--eas` and no platform flag, and skip the apps on local simulators. When `adb` gave no answer, an Android-shaped app stays unread instead of blocking the session's app, and the refusal for two unclaimed apps says to close the apps that are not the session's. ([#203](https://github.com/expo/expo-agent-cli/pull/203) by [@vonovak](https://github.com/vonovak))
- Runtime reads no longer read an app on a simulator that another worktree bound with a live lease. They skip it and name it on stderr; with only such apps connected, they refuse with `NO_APP_CONNECTED` and name the worktree. `runtime:reload` lists them in `skippedApps` and does not check their bundle. `smoke` now also skips another worktree's app, lists it in `skippedApps`, and names it and its worktree when no other app is connected. ([#204](https://github.com/expo/expo-agent-cli/pull/204) by [@vonovak](https://github.com/vonovak))

### 💡 Others

- `status` now summarizes itself as the check for Expo Go support and rebuild needs, the help notes explain `dev --plan`, `status` impact, and non-interactive `agents:setup`, and a failed `runtime:errors` suggests `dev:logs` to find bundling errors. ([#57](https://github.com/expo/expo-agent-cli/pull/57) by [@kudo](https://github.com/kudo))
- Every EAS command line this CLI prints — `Try:` lines, follow-ups, the needs-human `Ask the user` line, `How:` sentences — is now written with the runner this project would be run with: `npx --yes eas-cli@latest`, `npx --yes eas-cli` when the project pins the CLI, or `bunx eas-cli…` for a bun project. The old `npx eas …` spelling named a package that does not exist. ([#40](https://github.com/expo/expo-agent-cli/pull/40) by [@kudo](https://github.com/kudo))
